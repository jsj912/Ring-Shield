## T-P7 run settings (author decision, 2026-11-14, replacing runbook T-P7a/b batch size)

Phase 0 probes of MEGA-GenAgg (genagg/genagg, one train+val epoch, `--dry-run`, neighbours 100 100,
loader on its fallback route because the installed pyg-lib lacks edge-level temporal sampling;
pyg-lib is not to be installed or upgraded):

| Batch size | Seconds per epoch | Peak GPU memory (whole card, nvidia-smi) | val AP after epoch 1 |
|---|---|---|---|
| 8192 (the MEGA-GIN setting) | 1,078 | 24,173 MiB | 0.0302 |
| 4096 | 571 | 20,675 MiB (idle 387 MiB) | 0.1526 |

Rule:
- T-P7 runs at `--batch-size 4096`, `--num-neighs 100 100`, every other setting as the MEGA run (`experiments/R6_mega/config.yaml`). Batch size 8192 is not used: 4096 is about twice as fast per epoch (571 s against 1,078 s) and 8192 reaches the card's memory limit.
- Seed 1 first, in the background, capped at 15 hours, as the 0.70 gate, while T-P2 to T-P4 proceed.
- Stop and ask the author before seeds 2 to 5.
- If peak GPU memory during seed 1 goes above 23,000 MiB, or any epoch takes more than 900 s, stop the run and report.
- The results-table footnote states that the GIN-aggregation MEGA row used batch size 8192 and the GenAgg row 4096, because 8192 with GenAgg took 1,078 s per epoch and reached the 24 GB card's memory limit in a probe, against 571 s per epoch at 4096.
- The detector is MEGA-GenAgg (genagg at both stages). The adapter's recorded caveat applies: GenAgg as published has an inverse-objective forward hook that never fires.
